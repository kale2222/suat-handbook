# SUAT 校园助手大模型问答设计规格

- 日期：2026-07-16
- 状态：设计方向已确认，外部依赖待实施前核验
- 适用项目：SUAT 手册（Docusaurus 3.10）
- 关联设计：`design/2026-07-15-suat-campus-assistant-design.md`

## 1. 背景与设计原则

现有校园助手已经具备本地知识索引、中文关键词检索、来源展示、无依据拒答和故障降级。大模型的价值不是替代这些能力，而是把多个可靠来源归纳为更直接的短答案。

本阶段遵循以下原则：

1. 只有仓库文章和明确登记的 PDF 可以成为答案依据。
2. 错误硬答的伤害高于拒答；没有充分资料时必须拒答。
3. AI 不得影响普通访客的首屏性能，也不得成为手册可用性的单点故障。
4. 先使用现有关键词检索建立低成本基线；只有评测证明召回不足时，才引入向量检索。
5. 所有方案必须在当前免费额度和部署条件下可落地，并具有明确降级路径。

## 2. 目标与非目标

### 2.1 目标

1. 在现有 SUAT 校园助手中增加单轮大模型问答。
2. 综合一篇或多篇资料，输出约 100～200 字的中文回答。
3. 每个关键结论都能追溯到本次检索出的手册文章或 PDF。
4. 通过服务端检索、输出校验和明确拒答控制幻觉。
5. 在模型、额度、后端或数据库异常时，自动退回现有本地检索。
6. 匿名记录最小化的质量数据，形成内容与检索的改进闭环。
7. 模型供应商、具体模型和存储实现可替换，不与前端耦合。

### 2.2 非目标

本阶段不实现：

- 登录、学号认证、用户画像和个性化推荐；
- 多轮对话、聊天历史和跨设备会话；
- 网络搜索和模型自由补充校外知识；
- 向量数据库和 Embedding；
- 流式输出；
- 完整数据管理后台；
- 语音、图片或文件上传。

有限保留最近 2～3 轮上下文的追问能力进入未来需求池，只有真实问题证明有需要时才设计。

## 3. 产品形态与用户流程

### 3.1 页面分工

- 顶部搜索框继续承担免费、稳定的全站全文搜索。
- 下方 SUAT 校园助手升级为 AI 问答入口。
- 当前资料卡片保留为 AI 回答的来源区域和永久降级界面。

### 3.2 正常流程

1. 首屏只渲染轻量入口按钮。
2. 用户点击后才加载助手面板和浏览器本地知识索引。
3. 用户提交一个不超过 200 字的独立问题。
4. 后端检索仓库知识索引并判断资料是否充分。
5. 资料充分时调用模型归纳；资料不足时不调用模型。
6. 页面优先展示约 100～200 字的 AI 回答，随后展示引用来源和原文入口。
7. 用户可以反馈“有帮助”或“没帮助”。

### 3.3 回答边界

- 模型只能使用后端提供的检索片段。
- 不使用模型自身知识补充学校事实。
- 不访问互联网或引用仓库外网页。
- 来源链接由后端根据可信来源 ID 生成，不采用模型生成的 URL。
- 没有依据时显示“手册暂未收录”。
- 输入区明确提示不要提交姓名、学号、手机号等个人信息。
- 第一版非流式；等待时显示“正在查阅手册…”。

## 4. 总体架构

正式链路采用服务端关键词 RAG：

```text
Netlify 上的 Docusaurus 前端
  → Cloudflare Worker
    → 输入校验与限流
    → 服务端关键词检索
    → 置信度门槛
    → 缓存查询
    → Groq 模型适配器
    → 回答与引用校验
    → Cloudflare D1 匿名记录
```

降级链路为：

```text
Worker / Groq / D1 异常或额度耗尽
  → 前端现有本地检索
  → 展示资料卡片或“手册暂未收录”
```

职责边界：

- Netlify 只负责现有静态网站。
- Cloudflare Worker 负责 AI API、服务端检索、限流、缓存、日志和反馈。
- Cloudflare D1 保存低流量结构化数据。
- Groq 只负责受限上下文内的文本归纳。

前后端分开部署是由 Netlify 无可用后端/数据库额度这一现实约束产生。当前没有登录与 Cookie，因此跨域只需稳定 API 契约、允许来源列表和服务端限流。未来有自定义域名时，可以使用 `www` 与 `api` 子域统一品牌入口。

## 5. 服务端组件

### 5.1 问答接口

`POST /api/assistant/ask` 接收问题和前端当前加载的 `knowledge_version`。版本只用于与 Worker 内置版本做一致性校验；浏览器不发送检索片段、模型名称或密钥，也不能指定 Worker 使用哪个知识版本。

处理顺序：

1. 校验方法、内容类型、请求体大小和问题长度。
2. 拦截已知格式的学号、手机号等个人信息。
3. 执行短时来源限流和全站每日硬上限。
4. 比较前端与 Worker 的知识版本；不一致时停止 AI 链路并要求前端本地降级。
5. 加载 Worker 当前部署版本内置的知识索引。
6. 复用现有归一化、同义词和关键词检索算法。
7. 根据置信度决定回答或拒答。
8. 查询有效缓存。
9. 原子预留本次调用的 Token 预算。
10. 组装受长度限制的检索上下文并调用模型。
11. 校验回答结构、长度和引用 ID。
12. 返回回答、来源、状态、随机 `request_id` 与反馈凭证。
13. 以非阻塞方式写入匿名质量记录，并按实际 Token 对预算做保守校准。

### 5.2 知识索引

现有构建脚本仍然是唯一知识入口。每次构建生成内容哈希 `knowledge_version` 和同一份索引供两个消费者使用：

- 静态索引供浏览器本地检索和故障降级；
- Worker 部署包内的索引供正式 AI 链路检索。

同一提交先生成一次索引，再分别构建 Worker 与 Netlify 产物。部署后，前端每次请求携带自身加载的版本号，Worker 只接受与内置版本一致的请求。两个平台短暂不同步时直接本地降级，不能让旧前端使用新索引或新前端使用旧索引生成回答。

Worker 每次只选取少量高相关片段，并设置上下文 Token 上限。若关键词检索在固定评测集上无法达到召回目标，再设计“关键词 + 向量”的混合检索，不在本阶段预建向量设施。

### 5.3 模型适配器

首测候选配置为：

```text
provider: Groq
model: qwen/qwen3.6-27b
reasoning: none
streaming: false
max output: 首测 384 tokens，上线前按真实 P95 输出重新校准
```

模型名称通过非敏感环境配置提供，不写死在前端。适配器统一输入、输出、Token 使用量、限额和错误类型，使后续替换 Groq 模型或供应商时不修改检索与 UI。

模型返回一组结构化结论，而不是自由答案：

```text
claims[]:
  - text
  - evidence[]: source_id + chunk_id
```

服务端验证每条结论至少绑定一个本次检索到的 `source_id + chunk_id`，然后按顺序组合为最终回答。这样界面展示的每个结论都有明确证据映射。运行时服务端必须验证：

- 每个 `source_id + chunk_id` 属于本次检索结果；
- 每条结论都有非空证据数组；
- 回答不为空且未超出长度约束；
- 返回结构符合约定，且没有模型生成的外部 URL。

“引用内容是否真正支持关键结论”属于语义判断，不能宣称由简单代码完全保证。它通过受限 Prompt、固定离线评测和线上抽样审查控制，并作为发布硬门槛持续测量。

校验失败不自动重复调用模型，直接降级，避免一次问题产生多次 Token 消耗。

### 5.4 缓存

只有通过校验且不含疑似个人信息的回答可以缓存。缓存不保存明文问题，键使用服务端秘密计算 HMAC：

```text
HMAC(规范化问题)
+ 知识索引版本
+ Prompt 版本
+ 模型名称
```

缓存默认保留 7 天。文章、Prompt 或模型变化时，旧缓存因版本不同自然失效。

## 6. 数据与反馈

### 6.1 D1 数据

问答记录至少包含：

- `request_id`；
- 脱敏后的问题；
- 经校验的回答；
- 每条结论对应的 `source_id + chunk_id` 证据映射；
- `answered`、`not_found`、`fallback` 等结果状态；
- 模型与 Prompt 版本；
- 输入、输出 Token；
- 响应时间；
- 可空的反馈值；
- 创建与过期时间。

不建立用户表，不保存姓名、学号、原始 IP、浏览器指纹和长期会话轨迹。问答原始记录保留 90 天，之后删除；只允许保留不含原文和身份信息的汇总指标。

短时限流使用服务端秘密参与计算的 HMAC 摘要，并按天轮换输入。不能使用可枚举反推的普通 IP 哈希。摘要只用于计数，不写入问答记录，并在 48 小时内删除。

### 6.2 反馈接口

`POST /api/assistant/feedback` 接收 `request_id`、服务端签发的反馈凭证和 `helpful` / `unhelpful`。`request_id` 至少使用 128 bit 安全随机值；反馈凭证绑定对应请求并随问答记录过期。每个请求只接受第一次有效反馈，同时对反馈接口单独限流，降低枚举和数据污染风险。第一版不要求用户填写原因，也不建立管理后台；维护者可以定期导出汇总结果分析。

### 6.3 内容闭环

```text
匿名问题与反馈
  → 区分内容缺失、检索失败、生成失败
  → 补充文章 / 同义词 / 排序规则 / Prompt
  → 重建索引
  → 运行固定评测
  → 发布
```

## 7. 安全与隐私

1. `GROQ_API_KEY` 只保存为 Cloudflare Secret。
2. 本地开发使用被 Git 忽略的 `.dev.vars` 或 `.env`，仓库只允许无真实值的示例文件。
3. Worker 只接受允许方法、JSON 内容类型和受限大小的请求。
4. CORS 只允许生产站点和明确的本地开发来源，不使用 `*`。
5. CORS 不是身份认证；所有请求仍需服务端限流和每日硬上限。
6. 用户问题与知识片段在 Prompt 中明确分隔，用户无法覆盖“仅依据资料”的系统规则。
7. 明显个人信息在调用 Groq 前拒绝；日志写入前再次脱敏。自动识别是防御措施，不宣称覆盖所有开放文本。
8. 来源 URL 由可信来源 ID 映射生成。
9. 实施时增加密钥扫描；发现泄漏后立即吊销和轮换。
10. 手册与 PDF 中的文本同样视为数据，不允许其中的指令改变系统规则。

## 8. 额度与成本控制

成本保护按顺序执行：

1. 无可靠资料时不调用模型；
2. 有效缓存命中时不调用模型；
3. 单一来源短时间高频请求触发限流；
4. 达到全站每日硬上限后停止模型调用；
5. 所有超限请求自动降级为本地检索。

每日 AI 调用次数上限根据上线前实测决定，并预留 20% 免费 Token 缓冲。调用前，Worker 根据当前输入与配置上限计算保守预留量，通过 D1 原子条件更新预留预算；预留失败时不调用 Groq。调用成功后按实际 Token 校准，超时或无法获得用量时保留原预留量，宁可少用额度也不冒超支风险。

```text
每日 AI 调用次数上限
= 可用日 Token × 80% ÷ 实测单次 P95 Token
```

成本评价不只统计调用次数，还统计“每个可靠回答的 Token 消耗”：

```text
总 Token ÷ 通过质量校验的回答数
```

## 9. 异常处理与性能

| 情况 | 系统行为 |
| --- | --- |
| 检索依据不足 | 不调用 Groq，返回 `not_found` |
| Groq 超时、429 或 5xx | 返回降级状态，前端展示本地资料卡片 |
| 达到每日硬上限 | 停止调用 Groq，前端展示本地资料卡片 |
| 模型结构、长度或引用校验失败 | 丢弃模型输出并降级 |
| D1 日志写入失败 | 正常返回回答，质量日志失败不阻塞用户 |
| D1 限流或预算读写失败 | 不调用 Groq，前端展示本地资料卡片 |
| 知识版本不一致 | 不调用 Groq，前端展示当前版本本地资料卡片 |
| Worker 不可用 | 前端直接执行现有本地检索 |

性能要求：

- 首屏只加载轻量入口；面板和本地索引在首次点击后加载。
- 第一版非流式输出。
- P50 目标不超过 3 秒。
- P95 目标不超过 8 秒。
- 前端把 `answered`、`not_found`、`fallback`、`error` 和 `timeout` 作为明确状态处理。
- fetch 网络错误、CORS 错误、5xx、非 JSON 响应或 8 秒超时都触发本地降级；迟到回答不得再次覆盖界面。
- D1 日志以非阻塞方式写入。

## 10. 评测设计

### 10.1 第一性原理

北极星离线指标为：

```text
可靠解决率
= 正确回答且关键事实均有资料支撑的问题数
  ÷ 所有本应可以回答的问题数
```

核心安全护栏为：

```text
无依据硬答率
= 没有充分资料却仍生成具体答案的问题数
  ÷ 所有无依据问题数
```

拒答不是天然失败，错误硬答才是严重失败。检索、生成、引用、拒答、系统稳定性和成本必须分开计量，以便定位问题。

### 10.2 测试集

建立两层测试集：

1. 固定核心集约 100 题，其中约 70 题为可调试集、30 题为发布前保留集。每题由人工确认预期结果、必须来源、关键事实和禁止内容。
2. AI 扩展挑战集约 200 题。覆盖口语、错别字、校内但未收录、时效性、来源冲突、提示词攻击和隐私变体；大改检索、Prompt 或模型时运行，人工抽查。

少量真实学生表达只用于校准问题分布，不承担统计证明。上线后的匿名真实问题逐步替换合成问题。不能让同一个模型独立完成出题、回答和评分；AI 可以辅助评分，但发布门槛以结构化标准答案和人工审核为准。

### 10.3 上线门槛

| 层级 | 指标 | 初始门槛 |
| --- | --- | ---: |
| 严重错误 | 错误日期、费用、地点、流程等 | 固定评测集中为 0 |
| 边界 | 无依据硬答 | 固定发布集为 0；扩展集与线上抽样另报比例 |
| 引用 | 引用 ID 确实存在 | 100% |
| 引用 | 引用内容支持关键事实 | 固定发布集为 100%；扩展集趋势目标 ≥ 95% |
| 检索 | 正确资料进入前 5 条 | ≥ 90% |
| 多文档检索 | 所需资料全部被召回 | ≥ 80% |
| 生成 | 检索成功后的忠实回答率 | ≥ 95% |
| 完整性 | 覆盖标准答案关键点 | ≥ 85% |
| 拒答 | 无资料问题正确拒答率 | ≥ 95% |
| 过度拒答 | 有资料却拒答 | ≤ 10% |
| 安全 | 固定隐私与注入测试通过率 | 100% |
| 降级 | Worker / Groq 故障时本地检索可用 | 100% |
| 延迟 | P50 | ≤ 3 秒 |
| 延迟 | P95 | ≤ 8 秒，之后降级 |

这些数值是首测目标，不宣称是永久标准。第一次跑完现有本地检索基线后，应根据真实难度校准，但不得放宽严重错误、固定发布集无依据硬答、关键事实引用、引用合法和降级等硬门槛。发布前还需人工抽查扩展挑战集，不能只凭 30 道保留题得出统计性结论。

### 10.4 基线对比

必须在同一批问题上比较：

1. 现有本地关键词检索与资料卡片；
2. 服务端关键词检索；
3. 服务端关键词检索 + Groq 归纳。

重点验证跨文章问题是否更容易得到可靠结论，是否引入额外错误，以及每个可靠回答的 Token 和延迟。如果生成版只让文字更流畅，却没有提升可靠解决率，就不公开上线生成能力。

### 10.5 线上观察指标

- AI 回答率、未收录率和降级率；
- 反馈点击率及有帮助比例；
- 缓存命中率；
- Groq 调用成功率；
- P50、P90、P95 延迟与超时率；
- 平均及 P95 输入、输出 Token；
- 每个可靠回答的 Token；
- 高频未解决问题；
- 内容缺失、检索失败和生成失败的占比。

反馈好评率存在选择偏差，不能单独作为北极星指标；必须同时报告反馈覆盖率和离线质量审计结果。

## 11. 上线与回滚

1. **开发验证**：运行固定核心集、错误注入和密钥扫描。
2. **小范围内测**：使用保守每日上限，测量真实 Token、延迟、缓存和失败率。
3. **公开测试**：根据实测 P95 Token 计算每日上限，保留 20% 余量。

Worker 提供服务端启停配置。出现严重错误时停止 Groq 调用，前端继续使用本地检索，不需要关闭校园助手或静态网站。

## 12. 可行性结论

当前索引约 76 KB，适合同时供浏览器和 Worker 使用。预计每天 50～500 次提问、90 天最多约 4.5 万条记录，明显低于 Cloudflare Workers 和 D1 免费层的当前容量，但模型免费 Token 可能先成为约束，因此硬上限、缓存和本地降级是必需能力。

本方案不迁移现有 Netlify 网站，不新增登录系统，不预建向量数据库。实现工作集中在 Worker API、D1、模型适配器、前端结果状态和评测体系，边界清晰且可以分阶段验证。

根目录现有 `wrangler.toml` 用于静态资产部署。AI API 实施时使用独立的 Worker 入口和配置，不直接改写现有静态部署职责；部署前重新核对 Groq 模型可用性、账户实际限额以及 Cloudflare 免费层规则，避免把会变化的外部额度当作永久保证。

实施开始前必须完成外部依赖预检：候选模型 ID 可实际调用、中文评测通过、账户速率与 Token 限制已读取、超限行为已验证、Cloudflare Worker 与 D1 实际免费限额已确认。任一前提不成立时停留在本地检索版，不以未经验证的假设继续实现。

## 13. 分支与凭据策略

- 本设计规格保留在 `main`，作为产品与技术共同基线。
- API 实现继续在现有实验分支 `codex/suat-campus-assistant` 迭代，暂不合并。
- 实现前从 `main` 同步本设计文稿，但不覆盖实验分支现有功能。
- 真实 API Key、`.env`、`.dev.vars` 和其他本地凭据不得提交到任何分支或远端。
